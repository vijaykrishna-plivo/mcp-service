# aci-mcp-server — ACI-based replacement for nango-oauth + agent-mcp

Standalone folder that, once wired up, replaces **both** boxes of the current
CX platform integration stack with self-hosted [ACI.dev](https://github.com/aipotheosis-labs/aci):

| Today | This folder |
|---|---|
| **nango-oauth** — multi-tenant OAuth token custody | ACI linked accounts (per-tenant `linked_account_owner_id`, token storage + auto-refresh) |
| **agent-mcp** — MCP server with business-logic tools | `aci-mcp` SSE server over ACI's thin stock tools (raw provider REST, zero business logic) |

> **Deliberately thin.** Every tool is a declarative map to one provider endpoint —
> no business logic, no response-massaging / multi-call / compute (the LLM
> orchestrates). Tools come from three sources: ACI's stock catalog, our
> OpenAPI→ACI converter (`tools/openapi_to_aci.py`), and a few hand-written where
> no machine-readable spec exists. See `../aci-pilot/` for the measured cost data.

  empty-account / scope-limited / 3 bad keys — none broken).
- **Security:** an adversarial bug-hunt found 19 issues (2 critical); **both criticals are
  fixed and verified** — `connection_config` SSRF (write + execute guards) and bridge

- **Real LiveKit voice-agent** test passed against a live Google Calendar (read + book).

## How ACI is consumed (the "pip install or repo?" question)

Two pieces, both needed:

1. **ACI backend** — self-hosted from the repo (no pip package): docker compose
   stack (Postgres+pgvector, LocalStack KMS, PropelAuth mock, FastAPI server,
   runner). We reuse the clone at `../aci-pilot/aci/`; this folder only adds an
   override file and seeds.
2. **`aci-mcp`** — the MCP-protocol front-end, a Python package (`uvx aci-mcp`
   / `pip install aci-mcp`). It speaks MCP (SSE/stdio) to the agent and calls
   the backend's REST API (`/v1/functions/*/execute`). A clone also exists at
   `../aci-pilot/aci-mcp/` (verified to honor `ACI_SERVER_URL`); `run-mcp.sh`
   prefers it, falls back to uvx.

```
CX platform agent ──MCP/SSE──> aci-mcp (:8100) ──REST──> ACI server (:8000) ──> provider APIs
                                                              │
                                              linked accounts (per-tenant tokens)
```

```
  tools/openapi_to_aci.py# OpenAPI spec -> ACI thin-tool generator
  tools/tool_sweep.py    # 3-pass test suite (schema-valid / input-built / reaches provider)
  secrets/               # <app>.secrets.json.example per oauth2 app (fill + re-seed to enable linking)
  mock/embeddings_mock.py# deterministic embeddings fake (needed to seed without an OpenAI key)
  compose.override.yml   # mounts apps/scripts/secrets into ACI's runner + embeddings mock
  scripts/seed.sh        # upsert all apps + plans + project/agent (prints X-API-KEY)
  scripts/link-accounts.sh # app-configurations + account linking for tenant OWNER_ID
  scripts/run-mcp.sh     # single-tenant MCP server via stock aci-mcp (apps|unified mode)
  bridge/                # MULTI-TENANT MCP bridge (drop-in for agent-mcp's URL scheme)
  .env.example
```

## Runbook

```bash
cd aci-mcp-server

# 0. one-time: ACI backend env (cp from pilot if you already have it)
#    ../aci-pilot/aci/backend/.env.local must exist (see that repo's README)

# 1. bring up the ACI stack with our override
docker compose -f ../aci-pilot/aci/backend/compose.yml -f compose.override.yml \
  up -d --build db aws propelauth_mock embeddings-mock server runner

# 2. seed all 36 apps + get the agent API key (printed last — save it)
docker compose -f ../aci-pilot/aci/backend/compose.yml -f compose.override.yml \
  exec runner sh /workdir/cx-scripts/seed.sh

# 3. configure + link accounts for the tenant
#    api_key apps need CAL_API_KEY / SERPAPI_API_KEY env vars;
#    oauth2 apps print a browser URL each (needs secrets/<app>.secrets.json
#    filled + re-seed first — see secrets/README.md)
ACI_API_KEY=<key-from-step-2> ./scripts/link-accounts.sh

# 4. smoke-test a thin call directly against the backend
curl -X POST http://localhost:8000/v1/functions/GOOGLE_CALENDAR__CALENDARLIST_LIST/execute \
  -H "X-API-KEY: $ACI_API_KEY" -H "Content-Type: application/json" \
  -d '{"function_input":{},"linked_account_owner_id":"cx-tenant"}'

# 5. start the MCP server the CX platform will point at
ACI_API_KEY=<key> ./scripts/run-mcp.sh cx-tenant 8100
#    → SSE endpoint: http://localhost:8100/sse
#    MCP_MODE=unified for ACI's 2 meta-tools (search+execute) instead of 510 flat tools
```

## Replacement checklist — does this really cover both repos?

**nango-oauth (token custody) → ACI linked accounts.** Verified in the ACI
source (`aci/backend/aci/server/`):

| nango-oauth capability | ACI equivalent | verified where |
|---|---|---|
| Per-integration OAuth app config (client id/secret, scopes) | app.json `security_schemes.oauth2` + app-configuration | `apps/*/app.json` |
| Multi-tenant OAuth connect flow | `GET /v1/linked-accounts/oauth2` → browser consent → callback stores tokens | `routes/linked_accounts.py:312` |
| Token storage (per tenant) | `linked_accounts` table, secrets encrypted via KMS | upstream schema |
| **Automatic token refresh** | refreshed at execute time when expired; rotated refresh tokens persisted | `security_credentials_manager.py:87-127` |
| API-key style integrations | `POST /v1/linked-accounts/api-key` | used by `link-accounts.sh` |
| Connection list/delete per tenant | `GET/DELETE /v1/linked-accounts` | used by `link-accounts.sh` |

**agent-mcp (tool defining + serving) → ACI catalog + aci-mcp.**

| agent-mcp capability | ACI equivalent |
|---|---|
| Tool definitions in code (TS server classes) | JSON-only definitions (`apps/*/functions.json`, 510 tools) |
| MCP endpoint per tenant (`mcp_id`) | `aci-mcp` SSE server with `--linked-account-owner-id` (`run-mcp.sh`) |
| Tool execution with tenant creds | `POST /v1/functions/<NAME>/execute` — creds resolved server-side, token never leaves ACI |
| Business-logic tools (massage/multi-call/compute) | **intentionally NOT replaced** — thin raw tools only; that's the experiment |

**Differences to handle at wiring time** (the seam in the CX platform today is
agent-mcp calling the nango-backed credentials API — `agent-mcp/src/auth/client.ts`
fetches `{server_name, mcp_id} → token + custom_fields` at call time):

1. **Raw-token handout — SOLVED (broker).** For the secure default ACI executes the
   call itself and never returns the token. For legacy CX code that still wants the raw
   token (the nango pattern), `GET /v1/linked-accounts/credentials` brokers it back,
   refresh-on-read, keyed by `(app_name, linked_account_owner_id)`.
2. **Token import — SOLVED.** `POST /v1/linked-accounts/oauth2-import` ingests an
   existing access/refresh token (client_id/secret/scope taken from the app config) so
   nango connections migrate **without** re-consent; ACI refreshes them going forward.
3. **`custom_fields` per connection — SOLVED.** `connection_config` (JSONB on the linked
   account) is templated into the provider base URL at execute time
   (`server_url="https://{subdomain}.zendesk.com"` etc.). Values are validated as host
   labels (SSRF-guarded). Used by zendesk/freshdesk/shopify/confluence/jira/zoho/plivo.
4. ~~One aci-mcp process per tenant~~ **SOLVED — `bridge/`**: a multi-tenant
   MCP bridge replicating agent-mcp's URL scheme (`POST /:appName/:tenantId`,
   stateless streamable HTTP). One process, any number of tenants; the owner
   id is taken from the URL per request and stamped into ACI's execute call.
   Start: `cd bridge && bun install && ACI_API_KEY=<key> bun src/main.ts`
   (PORT default 8101). **Auth is fail-closed** — the bridge refuses to start with no
   auth. Set `BRIDGE_TENANT_TOKENS` (JSON `{"<bearer>":"<owner-id>"}`) for per-tenant
   binding (the URL tenant must equal the token's owner → cross-tenant access is `403`),
   or `BRIDGE_SECRET_KEY` for legacy shared-key mode. Verified: tools/list + tools/call
   route per-tenant; cross-tenant blocked; `zohodesk` aliases to ZOHO_DESK.

## Known constraints (inherited from the pilot findings)

- **Self-hosting is dev-grade upstream**: PropelAuth mocked, KMS via
  LocalStack, no production deployment guide. Fine for evaluation; a prod
  decision needs hardening work.
- **Token injection — now supported** via `POST /v1/linked-accounts/oauth2-import`
  (added in the fork): existing nango-held tokens can be migrated directly, no
  re-consent. The browser consent flow still works too.
- **Flat 510-tool MCP** degrades agent accuracy if all are exposed at once; for real use
  prefer per-agent app subsets (the bridge is per-app: `POST /:appName/:tenantId`) or
  ACI's `MCP_MODE=unified` (search+execute meta-tools). ACI's pgvector semantic search
  over tool embeddings is available to narrow large catalogs by intent.
- **Repo maintenance risk**: upstream ACI is on Dependabot life support
  (last real commit ~May 2026, company pivoted to consulting). Treat as a
  fork-and-own decision, not a dependency.

## Multi-tenancy mapping (for the eventual CX wiring)

- nango connection-id  →  ACI `linked_account_owner_id` (one per CX tenant)
- nango integration    →  ACI app-configuration (one per app, org-wide)
- agent-mcp MCP URL    →  `run-mcp.sh` SSE endpoint (`:8100/sse`), one process
  per tenant (the owner id is fixed per aci-mcp process — multi-tenant routing
  needs either one process per tenant or a thin proxy that injects the owner id).
